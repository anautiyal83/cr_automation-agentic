# Feature Specification: Agentic UC Pipeline

**Feature Branch**: `001-agentic-uc-pipeline`

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "An agentic framework using Google ADK that takes telecom UC documents (CIQ Excel, MOP, constraints, command outputs) as input, orchestrates LLM agents through a 9-step pipeline to generate, validate, and test CIQ validation rules, JSON templates, and workflow YAMLs — with automatic retry-on-test-failure feedback loops — producing deployment-ready artifacts and HTML test reports, all driven by a NiceGUI web UI with real-time progress tracking."

## Clarifications

### Session 2026-10-06

- Q: Should pipeline runs be persisted to durable storage or kept in-memory only? → A: Persist runs to durable storage; users can browse history.
- Q: Can a user cancel a pipeline run in progress, and what happens to partial artifacts? → A: Users can cancel; completed step artifacts are kept; in-progress step is discarded.
- Q: How should the system handle LLM API failures (rate limits, timeouts) distinct from test failures? → A: Separate retry mechanism — LLM API errors get their own retry count (e.g., 3 transient retries with exponential backoff) independent of the test-failure retry budget.
- Q: Is the mock simulator an existing component or built as part of this feature? → A: Mock simulator already exists in cr-automation; per-UC input/output configuration is required for each new use case.
- Q: Should there be automatic cleanup of pipeline run data and artifacts? → A: No automatic cleanup; provide a manual cleanup option in the UI where users select and delete specific artifacts.

### Session 2026-10-06 (Document Processing)

- Q: Does step 1 produce a unified intermediate structure or raw text for downstream steps? → A: Unified intermediate structure (canonical JSON/dict). Additionally, when the agent cannot derive required data from documents (e.g., ambiguous CIQ field validation rules, unclear MOP steps, missing command I/O mappings), the pipeline MUST pause with a Human-in-the-Loop (HIL) step to collect user input before proceeding. Pipeline MUST NOT advance until all necessary data is available.
- Q: How should the CIQ Excel file be parsed — by header names or fixed positions? → A: Header-name-based; agent identifies columns by header text, tolerant of reordering and extra columns.
- Q: What information is extracted from MOP documents? → A: MOPs provide CLI command templates, execution step sequences, and expected outputs — primary source for workflow YAML. MOPs can be CLI-based, REST API-based, or a mix of both. When the agent cannot clearly distinguish or extract commands/endpoints, HIL MUST engage.
- Q: What is the structure and purpose of the constraints file? → A: Mixed format — may contain structured tables (field constraints, value ranges) alongside free-form business rule descriptions. Agent extracts what it can; HIL engages for ambiguities.
- Q: What role do command output documents play? → A: Both — used to understand target system behavior for generation (command syntax, response format) AND as expected response patterns for mock simulator config and test assertions.

### Session 2026-10-06 (Testing)

- Q: Where does the real CIQ sample data for testing come from? → A: Self-contained — the uploaded CIQ Excel itself serves as the real test data. The pipeline tests generated configs against the same CIQ data used for generation.
- Q: Are test cases generated by the LLM or derived deterministically from configs? → A: Deterministic — test cases are derived automatically from generated configs. Validation rules applied to CIQ data, JSON templates verified against schema, workflows executed on mock simulator with responses checked against command output patterns.
- Q: What constitutes a "pass" for workflow testing against the mock simulator? → A: Response matching — pass if simulator responses match expected patterns from command output documents. Execution errors also fail.
- Q: Should HTML and Excel test reports contain identical content? → A: Complementary — HTML has full detail (interactive, expandable error traces, agent prompts); Excel has a structured summary (per-step pass/fail, error summaries, UC metadata) for QA sign-off and management review.
- Q: Should the system detect regressions when regenerating configs for the same UC? → A: Automated diff — system compares new generated configs against the last successful run for the same UC and flags differences in the test report, but does not block the pipeline.

### Session 2026-10-06 (LLM Usage)

- Q: Should each pipeline step use a dedicated agent or a single shared agent? → A: Dedicated agent per step with its own specialized prompt, orchestrated by a parent agent or pipeline controller. Aligns with Google ADK's multi-agent architecture.
- Q: How should the system handle documents exceeding the LLM context window? → A: Chunked processing — large documents split into manageable chunks, processed separately, results aggregated into the unified intermediate representation. No data loss.
- Q: Should agents use previously successful UC configs as few-shot examples? → A: Yes (strongly recommended) — dynamic few-shot selection from previously successful UC configs based on similarity to current UC type. Leverage growing knowledge base across many UCs.
- Q: How should the system ensure valid YAML output from LLM agents? → A: Structured output via ADK's tool-use/function-calling to enforce output schema at the LLM level, with lightweight post-processing as safety net. Cr-automation framework schema docs are provided to agents for better YAML generation understanding.
- Q: Should all steps use the same LLM model or support per-step model selection? → A: Per-step model configuration — each step can be assigned a different model via pipeline config with a default fallback. LLM calls are routed through OpenRouter via Python's liteLLM (not directly through Google's API).

### Session 2026-10-06 (UI)

- Q: Should the NiceGUI web UI be single-page or multi-page? → A: Single page with collapsible sections for all features.
- Q: What should the user see on first load (landing view)? → A: Upload form at top, with a summary table of recent pipeline runs below.
- Q: How should users find and filter past pipeline runs? → A: Filterable table with UC name, pass/fail status, and date range filters.
- Q: During an active pipeline run, can the user scroll to other sections? → A: Free scrolling; a sticky/pinned progress banner at top shows current step and status at all times.
- Q: Should per-UC mock simulator config be done via UI or config files? → A: Neither — simulator I/O config is auto-generated by the LLM agent after analyzing the command/API input-output documents provided as UC input.

### Session 2026-10-06 (UI Technology)

- Q: Should the UI use Streamlit or switch to a more capable Python UI framework? → A: Switch to NiceGUI — modern Python UI framework with Vue/Quasar components, native WebSocket real-time updates, and full layout control. Better suited for sticky progress banners, HIL inline forms, filterable tables, and collapsible sections.
- Q: Should the UI support dark/light theme or use a fixed theme? → A: Dark theme as default with a light/dark toggle for v1. Organizational branding (company colors, logo) planned for a later phase.
- Q: What should the UI settings section include? → A: A dedicated settings collapsible section for managing LLM API keys (OpenRouter), per-step model selection, retry limits, mock simulator endpoints, test data paths, and other pipeline configuration — all editable through the UI without requiring manual config file edits.

### Session 2026-10-06 (Pipeline Architecture Gaps)

- Q: What happens if a user never responds to a HIL request? → A: Pipeline waits indefinitely; no auto-timeout. User can return and resume from the exact paused step at any time. Option to restart from the paused step is available.
- Q: How should the system handle CIQ Excel files with multiple sheets? → A: All sheets and all columns are mandatory and processed by default. Sheets/columns are only excluded if explicitly specified by the user during upload or via the constraints file.
- Q: When test-failure retry is triggered, does the system retry only the failing step or re-run downstream steps too? → A: Smart cascading — retry the failing step; if it's a generation step (3-6) whose output feeds downstream steps, also re-run dependent steps (7-9) with the new output.
- Q: When the knowledge base has multiple configs for the same UC type, which is used for few-shot? → A: Latest only — each UC type retains only its most recent successful config in the knowledge base; older entries are replaced.
- Q: How does the system identify "same UC" for regression diff comparison? → A: UC name match — the user-provided UC name during upload is the identifier; exact name match links runs for regression diff.

## User Scenarios & Testing

### User Story 1 - End-to-End UC Onboarding via Pipeline (Priority: P1)

A telecom engineer uploads UC requirement documents (CIQ Excel, MOP document, constraints file, and sample command outputs) through the NiceGUI web UI. The system orchestrates 9 LLM agent steps to automatically generate all required YAML configs and optional Python scripts, tests them, and delivers deployment-ready artifacts with test reports.

**Why this priority**: This is the core value proposition — fully automated UC onboarding without code changes. Every other feature depends on this pipeline functioning end-to-end.

**Independent Test**: Can be fully tested by uploading a sample UC document set and verifying that 3 YAML configs are generated, tests pass, and HTML reports are produced.

**Acceptance Scenarios**:

1. **Given** the user has a complete set of UC documents (CIQ Excel, MOP, constraints, command outputs), **When** they upload all documents and trigger the pipeline, **Then** the system generates a validation rules YAML, a JSON template YAML, and a workflow YAML that pass schema validation.
2. **Given** the pipeline has generated configs, **When** automated tests execute against real CIQ data and the mock simulator, **Then** an HTML test report is produced showing per-step pass/fail results with timestamps.
3. **Given** a generated config fails a test, **When** the retry loop engages, **Then** the system feeds the error context back to the LLM agent and regenerates the failing config, up to a configurable retry limit.

---

### User Story 2 - Real-Time Progress Tracking (Priority: P2)

While the 9-step pipeline executes, the telecom engineer monitors progress in real time through the NiceGUI web UI. Each step's status (pending, in-progress, passed, failed, retrying) is visible, along with elapsed time and any error summaries.

**Why this priority**: Pipeline runs may take minutes; without visibility, users cannot distinguish a running pipeline from a stuck one, leading to duplicate submissions or premature cancellations.

**Independent Test**: Can be tested by triggering a pipeline run and verifying that the UI updates step-by-step status without requiring the user to refresh.

**Acceptance Scenarios**:

1. **Given** a pipeline run is in progress, **When** a step transitions from in-progress to passed or failed, **Then** the UI reflects the new status within 3 seconds without manual refresh.
2. **Given** a step has failed and the retry loop is active, **When** the system retries, **Then** the UI shows "retrying (attempt N of M)" with the error summary from the previous attempt.
3. **Given** all 9 steps have completed, **When** the pipeline finishes, **Then** the UI displays a summary with overall pass/fail, total duration, and a download link for test reports and generated artifacts.

---

### User Story 3 - Document Upload and Validation (Priority: P1)

The telecom engineer uploads UC requirement documents through the NiceGUI web UI. The system validates that the uploaded documents are in expected formats and contain the minimum required information before starting the pipeline.

**Why this priority**: Invalid or incomplete input documents waste pipeline execution time and LLM costs. Early validation prevents wasted effort and provides immediate, actionable feedback.

**Independent Test**: Can be tested by uploading valid and invalid document sets and verifying that the system accepts or rejects them with clear messages before pipeline execution begins.

**Acceptance Scenarios**:

1. **Given** the user uploads a valid CIQ Excel file, MOP, constraints, and command outputs, **When** the system validates the uploads, **Then** all documents pass pre-checks and the pipeline start button becomes enabled.
2. **Given** the user uploads a CIQ Excel file with missing mandatory columns, **When** the system validates the upload, **Then** a clear error message lists the missing columns and the pipeline cannot start.
3. **Given** the user uploads only a CIQ Excel file without the MOP or constraints, **When** the system validates the uploads, **Then** the UI indicates which additional documents are required.

---

### User Story 4 - Retry Feedback Loop with Error Context (Priority: P2)

When a generated YAML config or Python script fails testing, the system automatically retries by sending the failure details (error message, failing test case, expected vs. actual values) back to the LLM agent for a corrected generation. The user can observe retry attempts in the UI.

**Why this priority**: Retry with context is what makes the pipeline self-correcting rather than merely generative. Without it, every failure requires manual intervention.

**Independent Test**: Can be tested by providing a UC whose initial generation intentionally produces a known validation error, then verifying the system retries and the second attempt corrects the error.

**Acceptance Scenarios**:

1. **Given** a generated validation rules YAML fails against CIQ test data, **When** the retry loop activates, **Then** the LLM agent receives the specific validation error, the failing CIQ record, and the expected outcome as part of its retry prompt.
2. **Given** the retry limit (configurable, default 3) is reached, **When** all attempts have failed, **Then** the pipeline halts with a failure report containing all attempt histories and the user is notified.
3. **Given** a retry attempt succeeds, **When** the corrected config passes all tests, **Then** the pipeline continues to the next step without additional retries for that config.

---

### User Story 5 - Artifact Download and Deployment Packaging (Priority: P3)

After a successful pipeline run, the telecom engineer downloads all generated artifacts (3 YAML configs, optional Python scripts, HTML test reports) as a structured package ready for deployment into the cr-automation framework.

**Why this priority**: Generating artifacts has no value unless they can be easily consumed by the existing cr-automation framework. This story closes the loop from generation to deployment.

**Independent Test**: Can be tested by completing a successful pipeline run and verifying the downloaded package contains all expected files in the correct directory structure.

**Acceptance Scenarios**:

1. **Given** a pipeline run completed successfully, **When** the user clicks download, **Then** they receive a package containing validation_rules.yaml, json_template.yaml, workflow.yaml, any generated Python scripts, and the HTML test report.
2. **Given** the downloaded artifacts, **When** they are placed in the cr-automation framework's UC config directory, **Then** the framework processes CIQ data using those configs without errors.

---

### User Story 6 - Pipeline Step Configuration (Priority: P3)

An administrator configures pipeline parameters such as retry limits, LLM model selection, mock simulator endpoints, and test data paths through the NiceGUI web UI or a configuration file.

**Why this priority**: Different environments (dev, staging, production) and UCs may require different settings. Configuration avoids hard-coding and supports operational flexibility.

**Independent Test**: Can be tested by modifying retry limits and verifying the pipeline respects the new value during a test run.

**Acceptance Scenarios**:

1. **Given** an administrator sets the retry limit to 5, **When** a pipeline run encounters failures, **Then** the system retries up to 5 times before halting.
2. **Given** an administrator specifies a different LLM model, **When** the pipeline runs, **Then** all agent steps use the configured model.

---

### Edge Cases

- What happens when the CIQ Excel file contains multiple sheets with conflicting data? → All sheets are processed by default. Conflicts between sheets for the same field are flagged via HIL for user resolution. Sheets/columns can be excluded if specified by user or constraints file.
- How does the system handle LLM API rate limits or timeouts mid-pipeline? → Separate infrastructure retry with exponential backoff (up to 3 attempts), independent of test-failure retries. If exhausted, step fails with an infrastructure error distinct from a content error.
- What happens if the mock simulator is unreachable during testing? → Treated as an infrastructure failure; infrastructure retry mechanism applies. If unreachable after retries, step fails and pipeline halts with a connectivity error.
- How does the system handle a UC document set that is valid but describes a UC type the agents have never encountered? → Pipeline proceeds normally without few-shot examples. The agent relies on its system prompt, schema docs, and the intermediate representation. If generation quality is poor, the retry loop handles corrections. On success, the new UC is added to the knowledge base for future few-shot use.
- What happens when a retry produces a config that passes previously failing tests but fails a different test? → Since tests are deterministic and derived from configs, the full test suite re-runs on every retry attempt. If the new config passes the originally failing test but fails another, the retry loop continues with the new failure context fed back to the agent.
- How does the system behave if the user closes the browser during a pipeline run? → Pipeline continues server-side; run is persisted to durable storage. User can view results upon returning.

## Requirements

### Functional Requirements

- **FR-001**: System MUST accept UC document uploads in the following formats: CIQ as Excel (.xlsx/.xls — required), MOP as document file (.docx/.pdf/.txt — required), constraints as text or structured file (optional), and command outputs as text files (required).
- **FR-002**: System MUST validate uploaded documents for format correctness and minimum required content before pipeline execution begins.
- **FR-003**: System MUST orchestrate a 9-step LLM agent pipeline using Google ADK, where each step has a defined input, output, and success criteria.
- **FR-004**: The 9 pipeline steps MUST include: (1) document parsing and extraction, (2) UC requirements analysis, (3) validation rules generation, (4) JSON template generation, (5) workflow generation, (6) optional Python script generation + mock simulator I/O config generation, (7) schema validation of all generated configs, (8) test execution against CIQ data and mock simulator, (9) test report generation.
- **FR-005**: System MUST generate three YAML configuration files per UC: validation rules, JSON template, and workflow — each conforming to the cr-automation framework's schema.
- **FR-006**: System MUST optionally generate Python scripts when transformation logic cannot be expressed in YAML alone, as determined by the LLM agent during generation.
- **FR-007**: System MUST automatically retry failed test steps by feeding error context (error message, failing test case, expected vs. actual) back to the LLM agent, up to a configurable retry limit (default: 3). Retry MUST use smart cascading: retry the failing step, and if it is a generation step (3-6) whose output feeds downstream steps, also re-run dependent steps (7-9) with the regenerated output.
- **FR-008**: System MUST execute generated configs against the uploaded CIQ Excel data during the test step. The uploaded CIQ serves as both the source for generation and the test data — no separate test data upload is required.
- **FR-009**: System MUST execute generated workflow configs against the mock simulator. A workflow test MUST pass only if simulator responses match expected patterns derived from the command output documents. Execution errors also constitute a failure.
- **FR-010**: System MUST produce an HTML test report and an MS Excel test report for every pipeline run, regardless of pass/fail outcome. The HTML report MUST contain full detail (per-step results, timestamps, error traces, expandable agent prompts/responses, actual vs. expected values). The Excel report MUST contain a structured summary (per-step pass/fail, error summaries, UC metadata) suitable for QA sign-off and management review.
- **FR-011**: System MUST provide a NiceGUI-based single-page web UI with collapsible sections for document upload, pipeline progress, run history, artifact cleanup, and settings. Users MUST be able to freely scroll between sections at all times, including during active pipeline runs. NiceGUI's Vue/Quasar components and native WebSocket support MUST be leveraged for real-time updates, sticky progress banners, and inline HIL response forms.
- **FR-041**: The UI MUST default to a dark theme and provide a light/dark theme toggle. Quasar's built-in dark mode support MUST be used.
- **FR-042**: LLM API keys MUST be stored securely and displayed masked (e.g., `sk-...xxxx`) in the Settings UI. Keys MUST NOT be logged in pipeline execution logs or included in test reports.
- **FR-012**: System MUST display real-time pipeline progress in the UI, updating step statuses (pending, in-progress, passed, failed, retrying) without requiring manual page refresh. During an active run, a sticky/pinned progress banner MUST remain visible at the top of the page as the user scrolls to other sections.
- **FR-013**: System MUST allow users to download all generated artifacts and test reports as a structured package after pipeline completion.
- **FR-014**: System MUST allow configuration of pipeline parameters via a dedicated Settings section in the UI. The Settings section MUST include:
  - **LLM API keys**: OpenRouter API key management (stored securely, masked in UI)
  - **Per-step model selection**: Assign LLM models to individual pipeline steps with a default fallback
  - **Retry limits**: Configurable retry count for both test-failure retries and infrastructure retries
  - **Mock simulator endpoints**: Target simulator URL/connection settings
  - **Test data paths**: Paths to test data directories
  - **Pipeline defaults**: Default UC name prefix, output directory, report format preferences
  - Settings MUST persist across sessions and be editable through the UI without requiring manual config file edits. Config files MAY still be used as the underlying storage mechanism.
- **FR-015**: System MUST log all pipeline executions, including agent prompts, responses, test results, and retry attempts, for auditability.
- **FR-016**: System MUST halt the pipeline and notify the user when the retry limit is exhausted without a passing result.
- **FR-017**: System MUST preserve CIQ data fidelity throughout the pipeline — no silent data drops or alterations.
- **FR-018**: System MUST persist all pipeline run data (status, timestamps, step results, generated artifacts, retry histories) to durable storage so users can browse and review historical runs.
- **FR-019**: System MUST allow users to cancel a running pipeline. On cancellation, artifacts from completed steps MUST be retained; the in-progress step MUST be discarded. The pipeline run MUST be recorded with a "cancelled" status.
- **FR-020**: System MUST implement a separate retry mechanism for LLM API infrastructure failures (rate limits, timeouts, network errors) independent of the test-failure retry budget. Infrastructure retries MUST use exponential backoff with a configurable retry count (default: 3).
- **FR-021**: System MUST auto-generate per-UC mock simulator input/output configuration via the LLM agent, by analyzing the command/API input-output documents provided as UC input. The generated simulator config MUST define expected CLI commands and simulated responses for the mock simulator in cr-automation.
- **FR-022**: System MUST provide a cleanup interface in the UI where users can select and delete specific pipeline run artifacts. No automatic cleanup policy is applied.
- **FR-023**: The UI landing view MUST display the document upload form at the top with a summary table of recent pipeline runs below.
- **FR-024**: The run history section MUST provide a filterable table with UC name, pass/fail status, and date range filters.
- **FR-026**: Pipeline step 1 (document parsing) MUST produce a unified intermediate structured representation (canonical JSON/dict) from all uploaded documents. All subsequent agent steps MUST consume this structure, not raw document text. CIQ Excel parsing MUST be header-name-based, identifying columns by header text and tolerating column reordering and extra columns.
- **FR-031**: MOP documents MUST be parsed to extract CLI command templates, REST API call definitions, execution step sequences, and expected outputs. The system MUST support MOPs that are CLI-based, REST API-based, or a mix of both. When the agent cannot clearly distinguish or extract commands/endpoints from the MOP, HIL MUST engage.
- **FR-032**: Constraints files MUST be parsed supporting mixed formats — structured tables (field constraints, value ranges, cross-field dependencies) alongside free-form business rule descriptions. The agent MUST extract structured constraints automatically and engage HIL for ambiguous or free-form rules that cannot be reliably interpreted.
- **FR-033**: Command output documents MUST serve a dual purpose: (1) teaching the agent the target system's command syntax and response format to inform config generation, and (2) providing expected response patterns for mock simulator I/O configuration and test assertions.
- **FR-034**: Each of the 9 pipeline steps MUST be implemented as a dedicated agent with its own specialized prompt, orchestrated by a parent agent or pipeline controller. Agents MUST NOT share conversational state across steps; inter-step communication MUST occur through the intermediate representation and step outputs.
- **FR-035**: When UC documents exceed the LLM context window, the system MUST split them into manageable chunks, process each chunk separately, and aggregate results into the unified intermediate representation. No data MAY be silently dropped due to context window limits.
- **FR-036**: The system MUST dynamically select relevant examples from previously successful UC configs as few-shot context in agent prompts. Selection MUST be based on similarity to the current UC type. As the system processes more UCs, the few-shot knowledge base MUST grow automatically.
- **FR-037**: Agent YAML output MUST be enforced via Google ADK's structured output / tool-use / function-calling capabilities to guarantee schema-valid output at the LLM level. Cr-automation framework schema documentation MUST be provided to generation agents as reference context. A lightweight post-processing validation MUST serve as a safety net.
- **FR-038**: Each pipeline step MUST support independent LLM model configuration. The pipeline configuration MUST allow assigning a different model per step with a default model as fallback. LLM calls MUST be routed through OpenRouter via liteLLM, enabling access to any model available on OpenRouter.
- **FR-027**: When the agent cannot derive required information from documents during parsing and analysis (e.g., ambiguous CIQ field validation rules that cannot be inferred from field type, unclear MOP procedural steps, missing command I/O mappings), the pipeline MUST pause execution and present a Human-in-the-Loop (HIL) step in the UI requesting specific input from the user.
- **FR-028**: The pipeline MUST NOT proceed past the document analysis phase (steps 1-2) until all necessary data for config generation is collected — either from documents or via HIL user input. Simple field types (string, email, numeric) MAY be auto-inferred; complex or ambiguous validation constraints MUST be confirmed via HIL.
- **FR-029**: The HIL step MUST present the user with the specific field, document section, or command that requires clarification, along with what the agent has already inferred, and request a targeted answer. The UI MUST support the user responding inline without restarting the pipeline.
- **FR-030**: Pipeline state MUST be preserved while waiting for HIL input indefinitely (no auto-timeout). The pipeline MUST resume from the exact point of interruption after the user provides the requested information. Users MUST also have the option to restart the pipeline from the paused step.
- **FR-039**: Test cases MUST be derived deterministically from generated configs, not generated by the LLM. Validation rules MUST be applied to CIQ data to verify correct acceptance/rejection. JSON templates MUST be populated and verified against schema. Workflow steps MUST be executed on the mock simulator with responses checked against expected patterns from command output documents.
- **FR-040**: When a pipeline run produces configs for a UC that has a previous successful run, the system MUST automatically compare new generated configs against the last successful configs for that UC. "Same UC" is determined by exact match on the user-provided UC name during upload. Differences MUST be flagged in the test report as a regression diff section. This comparison MUST NOT block the pipeline.
- **FR-043**: All sheets and all columns in a CIQ Excel file MUST be processed by default. Sheets or columns are excluded only if explicitly specified by the user during upload or defined in the constraints file. A conflict exists when multiple sheets define the same column header with different values for the same logical record (matched by a common key field such as row index or site identifier). When such conflicts are detected, the system MUST flag the conflict via HIL, presenting the conflicting values and asking the user which to use.
- **FR-044**: The few-shot knowledge base MUST retain only the most recent successful config per UC type (identified by UC name). When a new successful run completes for a UC that already has a knowledge base entry, the older entry MUST be replaced with the new one.

### Key Entities

- **UC Document Set**: A collection of uploaded files (CIQ Excel, MOP, constraints, command outputs) representing a single use case's requirements.
- **Pipeline Run**: A single execution of the 9-step agent pipeline for one UC document set, with its status, timestamps, and results.
- **Generated Config**: A YAML file (validation rules, JSON template, or workflow) produced by an LLM agent step.
- **Test Execution**: A run of generated configs against CIQ test data and the mock simulator, producing pass/fail results.
- **Retry Attempt**: A re-execution of a failed agent step with error context appended to the agent prompt.
- **Test Report**: An HTML document summarizing test execution results, including per-step outcomes, actual vs. expected values, and error traces.
- **Pipeline Configuration**: Settings governing pipeline behavior (retry limits, model selection, endpoints, test data paths).
- **Pipeline Run History**: Durable record of all pipeline runs, persisted to storage, browsable by users for audit and comparison.
- **Intermediate Representation**: A unified canonical JSON/dict structure produced by step 1 from all uploaded documents, serving as the single input contract for all downstream agent steps.
- **HIL Request**: A Human-in-the-Loop pause event where the pipeline presents an unresolvable data gap to the user and waits for their input before resuming.
- **Few-Shot Knowledge Base**: A growing collection of previously successful UC configs used as dynamic few-shot examples in agent prompts, selected by similarity to the current UC type.
- **Agent Step**: A dedicated LLM agent with a specialized prompt handling one pipeline step, orchestrated by a parent controller. Each agent operates independently with no shared conversational state.
- **Regression Diff**: An automated comparison between newly generated configs and the last successful configs for the same UC, included in the test report to flag changes without blocking the pipeline.

## Success Criteria

### Measurable Outcomes

- **SC-001**: A telecom engineer can onboard a new UC from document upload to deployment-ready artifacts in under 30 minutes, without writing any code.
- **SC-002**: The retry feedback loop resolves at least 70% of first-attempt test failures without human intervention.
- **SC-003**: Every pipeline run produces a complete HTML test report within 60 seconds of pipeline completion.
- **SC-004**: The UI reflects pipeline step status changes within 3 seconds of the underlying event.
- **SC-005**: Generated YAML configs pass schema validation on every successful pipeline run (100% schema conformance).
- **SC-006**: The system supports onboarding 10 different UC types without any framework code changes.
- **SC-007**: 90% of users can successfully upload documents and trigger a pipeline run on their first attempt without external guidance.

## Assumptions

- The cr-automation framework (ciq-processor, cli-automation-standalone) is available as a stable dependency and its YAML schema definitions are documented and accessible.
- Google ADK is the mandated agent orchestration framework; no alternative agent frameworks are in scope.
- The mock simulator already exists in the cr-automation framework; it requires per-UC input/output configuration (expected CLI commands and simulated responses) for each new use case.
- CIQ Excel files follow a known structure with identifiable mandatory columns (parsed by header name, not position), though column names may vary by UC type.
- Constraints files may be mixed-format (structured tables + free-form text); no single enforced schema is assumed.
- Command output documents contain real CLI/API session logs with commands and their responses; they may include prompts, banners, or other noise that the agent must filter.
- LLM calls are routed through OpenRouter via Python's liteLLM library, not directly through Google's API. Google ADK is used for agent orchestration (multi-agent architecture, tool-use, structured output) while liteLLM handles model routing.
- Users have network access to the OpenRouter API endpoint from the environment where the NiceGUI app runs.
- Cr-automation framework schema documentation is available and will be provided to generation agents as reference context for YAML output.
- The NiceGUI web UI is intended for internal telecom engineering teams, not external customers; enterprise-grade authentication is out of scope for the initial version.
- MS Excel test reports (referenced in the constitution) will be generated alongside HTML reports. HTML contains full interactive detail for engineers; Excel contains a structured summary for QA sign-off and management review.
- Pipeline runs are single-user operations; concurrent multi-user pipeline execution is not required for the initial version.
- UC requirement documents are in English.
