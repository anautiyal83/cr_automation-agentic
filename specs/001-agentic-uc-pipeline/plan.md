# Implementation Plan: Agentic UC Pipeline

**Branch**: `001-agentic-uc-pipeline` | **Date**: 2026-10-06 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-agentic-uc-pipeline/spec.md`

## Summary

Build a Python-based agentic framework using Google ADK that orchestrates 9 dedicated LLM agents through a pipeline to automatically generate, validate, and test YAML configs (validation rules, JSON template, workflow) from telecom UC documents. The system uses existing cr-automation Java modules (ciq-processor for CIQ validation/JSON generation, cli-automation-standalone for MOP execution) for testing, includes automatic retry-on-failure feedback loops, Human-in-the-Loop steps for ambiguous data, and a NiceGUI web UI with real-time progress tracking. LLM calls route through OpenRouter via liteLLM with per-step model configurability.

## Technical Context

**Language/Version**: Python 3.11+

**Primary Dependencies**:
- Google ADK (agent orchestration, multi-agent, tool-use/structured output)
- liteLLM (LLM routing through OpenRouter)
- NiceGUI (web UI — Vue/Quasar components, WebSocket real-time)
- openpyxl (CIQ Excel parsing)
- python-docx / PyPDF2 (MOP document parsing)
- PyYAML / ruamel.yaml (YAML generation and validation)
- Jinja2 (prompt templating)
- openpyxl + xlsxwriter (Excel report generation)
- Jinja2 (HTML report templating)
- SQLite / TinyDB (pipeline run persistence)
- scikit-learn or sentence-transformers (few-shot similarity matching)

**External Java Modules (invoked as subprocess/CLI)**:
- ciq-processor: CIQ validation and JSON generation — standalone JAR
- cli-automation-standalone: CLI/REST workflow execution and mock simulator — standalone JAR

**Storage**: SQLite for pipeline run metadata + file system for generated artifacts and reports

**Testing**: pytest (unit + integration), ciq-processor JAR (CIQ validation tests), cli-automation-standalone JAR (workflow tests against mock simulator)

**Target Platform**: Linux/Windows server, single-user web app (internal telecom engineering teams)

**Project Type**: Web application (Python backend + NiceGUI frontend, single codebase)

**Performance Goals**: Pipeline completion < 30 minutes per UC (SC-001), UI status updates < 3 seconds (SC-004), report generation < 60 seconds (SC-003)

**Constraints**: Single-user (no concurrent pipelines for v1), LLM calls via OpenRouter (network dependency), Java modules invoked as external processes (JRE required)

**Scale/Scope**: 10+ UC types without code changes (SC-006), growing few-shot knowledge base, single-user deployment

**Structure Decision**: Single Python project with modular package layout. Steps 7-9 (schema validation, test execution, report generation) are consolidated into `src/agents/` alongside LLM agents for uniform step interface, despite being deterministic (no LLM). Report Jinja2 templates live in `src/testing/report/templates/`. The `src/` directory contains all application code organized by responsibility: `agents/` for LLM agent definitions, `core/` for pipeline engine, `parsers/` for document parsing, `testing/` for test harness and reporting, `knowledge/` for few-shot store, `ui/` for NiceGUI interface, `storage/` for persistence, and `prompts/` for externalized prompt templates. External Java modules (ciq-processor, cli-automation-standalone) are invoked as subprocess calls.
